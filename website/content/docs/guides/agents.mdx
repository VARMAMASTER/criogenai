An **agent** is a model plus tools, run as a loop: the model answers or asks
for tool calls, the tools run, the results go back, until the model answers
without calling a tool (or a limit is reached).

## Tools, limits and typed output

<Sample name="agents" />

In Rust, typed output is a JSON Schema:

<Sample name="agents" region="structured" only={["rust"]} />

- **Arguments are validated** against the schema before your function runs
  ([how](/docs/concepts/messages-and-tools/)).
- **Limits** stop runaway loops: `model_calls` (default 25), `tool_calls`
  (200), `tokens`, and a timeout per tool call (60 s). Reaching one fails
  the run with `limit_exceeded`.
- **Typed output** makes the run end with JSON matching a schema (in Python,
  a Pydantic model). Invalid answers go back to the model with the
  problems. Models with a JSON mode answer in it; others call a reserved
  `final_output` tool.

In TypeScript, a tool's `input` can also be a Zod schema, or any
[Standard Schema](https://standardschema.dev) (ArkType, Valibot). The
engine checks the JSON Schema the library makes; then the library checks
what JSON Schema cannot say (refinements), and its issues go back to the
model as invalid arguments. `run` receives the library's output, with
defaults and transforms applied, and its type is inferred. Valibot cannot
make a JSON Schema itself: pass `jsonSchema: toJsonSchema(schema)` (from
`@valibot/to-json-schema`).

## The result

| Field (Python / TypeScript) | Rust | Meaning |
|---|---|---|
| `text` | `result.text()` | The final answer |
| `output` | `result.output` | The typed output, if you asked for one |
| `messages` | `result.messages` | The whole transcript |
| `usage` | `result.usage` | Tokens across all model calls |
| `model_calls`, `tool_calls` / `modelCalls`, `toolCalls` | same names | How much the run did |
| `needs_approval`, `approvals` / `needsApproval`, `approvals` | `is_suspended()`, `approval_requests()` | Paused for a person |

## Testing

Use `FakeModel` in tests: scripted replies (text or tool calls) in order,
with no network. In Rust it can also fail on purpose (`failing_on`,
`flaky_first`) to test error handling.

## Sub-agents

An agent can be a tool of another agent: the tool takes a question
(`input`) and returns the sub-agent's answer. How deep agents may call
agents is limited (8 by default). An agent can also be one step of a
[workflow](/docs/guides/workflows/).

## Hooks

Hooks run your code around the loop: at the start and end of a run, and
before and after every model call and tool call. Use them to block or
change a tool call, hide data from the model, answer from a cache, or stop
a run early. A hook is an object with any of these methods (sync or async):

<Sample name="agents" region="hooks" />

| Python | TypeScript | When | It may |
|---|---|---|---|
| `on_start(ctx)` | `onStart(ctx)` | once per run (and per resume or retry) | save state for later calls: `HookAction(state=…)` |
| `before_model(ctx)` | `beforeModel(ctx)` | before each model call | replace the transcript (`messages`), or end the run (`end`, `output`) |
| `after_model(ctx)` | `afterModel(ctx)` | after each model reply | replace the reply (`message`), or end the run |
| `before_tool(call)` | `beforeTool(call)` | before each tool call | change the call (return it), skip the tool (`ToolResult(value)`), or raise `ToolError` |
| `after_tool(call, result)` | `afterTool(call, result)` | after each tool call | return a replacement result |
| `on_end(ctx, outcome)` | `onEnd(ctx, outcome)` | always, once per run | nothing (it cannot change the outcome) |

`ctx` has the run id, the messages so far, the number of model calls, the
hook's saved state and the run state. Hooks run in list order, and the
"after" methods in reverse order, like layers. An exception in
`on_start`, `before_model` or `after_model` fails the run with
`hook_failed` (what was raised is the error's cause); one in a tool hook
counts as the tool's own exception (see the tool exception setting above).
In Rust, a hook implements `Hook`, with `wrap_tool` and `wrap_model` around
each call instead of a before and an after method.
