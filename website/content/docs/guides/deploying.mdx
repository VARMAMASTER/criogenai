Criogen runs inside your server process: there is no Criogen service to
deploy. Your web app imports the package, builds its agents once, and calls
them from request handlers; the browser talks to your server, never to the
engine or a model provider. This page shows that setup with FastAPI and
Next.js, then covers storage, keys, serverless and the gateway. For health
checks, redaction, cost and tracing, see
[Using Criogen in your app](/docs/guides/production/).

## The shape of a deployment

```
browser ──HTTP──► your server (FastAPI, Next.js, Express, ...)
                    │  one Storage and one Agent per process
                    ├──► model provider (OpenAI, Anthropic, Ollama on your network, ...)
                    └──► database (SQLite file, or Postgres for several processes)
```

Rules that hold everywhere:

- **Build once, use per request.** Create the `Storage` and the agents at
  start-up (module level, or a cached function). They are safe to use from
  many requests at once. Make a thread handle per request; it holds nothing
  but the id.
- **Who the user is comes from your authentication**, not from the request
  body: the thread id they may open, the `user_id` for memory, the `actor` for
  the audit trail.
- **Return error codes, not messages.** A message can quote what a tool or the
  model saw.
- **Close the storage at shutdown** (`await storage.close()`).

## FastAPI (Python)

The tutorial's agent behind three routes: send a message, stream a message,
approve a refund. `customer_of` and `staff_of` stand for your own
authentication.

<Sample name="deploy" only={["python"]} />

```sh
pip install criogen fastapi uvicorn
DATABASE_URL=postgres://app:secret@db.internal/agents uvicorn deploy:app --workers 4
```

- Use the `async` methods (`await chat.send(...)`) in async routes. The
  `*_sync` methods refuse to run inside an event loop.
- Several workers are several processes: use Postgres, so they share threads
  and one-run-per-thread holds across them.

The engine is native code, so the route runs on the **Node.js runtime**, not
Edge, and the package stays out of the bundle:

```js
// next.config.mjs
export default { serverExternalPackages: ["criogen"] };
```

`request.signal` cancels the run when the client goes away; on a thread the
run is saved and `retry()` continues it. Leave the signal out if a turn should
finish even when the user closes the page.

Express, Fastify, Hono on Node.js and NestJS work the same way: build the
agent once, call it in the handler, map `CriogenError.code` to a status.

## Storage for your deployment

| Deployment | Storage |
|---|---|
| One process on one machine (a VM, a container with one worker) | SQLite on a persistent disk |
| Several workers or replicas | Postgres |
| Serverless functions | Postgres (the local disk is not kept, and instances run in parallel) |
| Tests and previews | In memory |

With Postgres, use a direct connection or PgBouncer in **session** mode, and
TLS for a database on another machine. More in
[Storage](/docs/guides/storage/#postgres-in-production).

## Keys and settings

- Models read their keys from environment variables (`OPENAI_API_KEY`,
  `ANTHROPIC_API_KEY`, ...). Set them in your platform's secret settings.
- `load_env()` / `loadEnv()` reads a `.env` file into the environment for
  local development; it never prints a value and never replaces a variable
  that is already set. Keep `.env` out of version control.
- Building an agent with a hosted model and no key fails at start-up with the
  name of the variable to set, not on the first request.
- Self-hosted models (Ollama, vLLM, LM Studio) need no key. A key is never
  sent over plain `http://` to another machine unless you allow it
  explicitly.

## Health checks

`ready()` checks that the engine loads, and with a model, that the model
answers (one tiny call). It never throws, so it fits a `/health` route:

```python
report = await criogen.ready("openai:gpt-5-mini")   # {"ok": ..., "engine": {...}, "model": {...}}
```

```ts
const report = await ready({ model: "openai:gpt-5-mini" });
```

Without a model it only checks the engine, which costs nothing: use that for
frequent liveness probes, and the model check less often.

## Serverless

| Platform | Works |
|---|---|
| Functions on **Node.js 18+** or **Python 3.9+**, Linux x64 or ARM64 with glibc 2.28 or newer (the Node.js runtimes of AWS Lambda and Vercel, for example) | yes |
| Edge runtimes (Vercel Edge, Cloudflare Workers) | not with the native package; `criogen/web` runs the engine as WebAssembly but is not yet tested there ([In the browser](/docs/guides/browser/)) |
| Alpine Linux (musl) images | not yet: use a Debian or Ubuntu based image |

On serverless:

- Use Postgres: a function's disk is not kept between invocations.
- A function may be frozen as soon as it returns a response. Finish the turn
  (or the stream) before returning, rather than continuing in the
  background.
- Approvals fit well: a run pauses, the function returns, and a later
  invocation (a webhook, a staff action) calls `approve()` on the same thread.
- Function time limits apply to the whole turn, model calls and tools
  included. Set `limits` and tool timeouts below your platform's limit.

<Aside type="caution" title="Engine versions on Linux and macOS">
The latest engine (0.1.6) is published for Windows x64 and the browser. On
Linux and macOS, `pip` installs 0.1.3 and npm runs the 0.1.3 engine until
their builds run again. Features marked 0.1.5 or 0.1.6 on the
[status page](/docs/status/) are not in the 0.1.3 engine: check before you
deploy to a Linux server.
</Aside>

## The LLM gateway

`criogen-gateway` is a separate server that speaks the OpenAI and Anthropic
APIs in front of any provider, with virtual keys, rate limits, token budgets
and usage records ([The LLM gateway](/docs/guides/gateway/)). It is part of
the Rust crates, which are published when Criogen's code opens; from Python
and TypeScript today, the `Gateway` class gives the same routing, retries and
fallbacks inside your process
([Models: call a model directly](/docs/guides/models/#call-a-model-directly)).

## Checklist

- [ ] Agents and storage built once per process; `close()` at shutdown.
- [ ] Postgres if more than one process or any serverless function.
- [ ] Keys in the platform's secrets; `.env` only on developer machines.
- [ ] User identity, thread ids and actors from your authentication.
- [ ] Error codes, not messages, in responses.
- [ ] `limits` and timeouts below the platform's request limit.
- [ ] A `/health` route with `ready()`.
- [ ] For sensitive data: `redact`, [encryption, audit and retention](/docs/guides/compliance/).
